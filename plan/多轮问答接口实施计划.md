# 多轮问答接口实施计划

> 面向项目：`rag-xmut-main`（Spring Boot 4.1.1 + Java 21 + Spring AI 2.0 + Milvus + LM Studio 本地模型）
> 目标：新增一个**支持多轮对话的知识库问答接口**（提问接口），即「多轮 + RAG 知识增强」问答。
> 前置说明：本文仅作计划，**不涉及任何代码改动**。用户确认后（点击批准）再进入编码实施。
> 日期：2026-09-10

---

## 一、背景与目标

### 1.1 项目现状（已核实）
| 项 | 现状 |
| --- | --- |
| 现有对话接口 | `POST /api/chat`，`ChatRequest{message}` → `ChatService.chat(message)` → 模型，**纯单轮、无记忆** |
| 知识库 | `RagKnowledgeService` 已可导入/检索（`search(query, topK)` → Milvus 集合 `knowledge_base`），但**对话从未使用它** |
| 现有类文件 | `ChatController` / `ChatService` / `ChatRequest` / `ChatResponse` / `ChatConfig` / `RagKnowledgeService`(含 VectorStore) |
| 测试现状 | 仅 `RagApplicationTests.contextLoads()`，**无任何单元/集成测试**，无覆盖率插件 |

### 1.2 目标
1. 提供一个多轮问答接口：后续提问能"记住"前文（按 `sessionId` 划分会话）。
2. 问答**自动结合知识库**（RAG）：从 Milvus 检索相关知识注入模型，回答有出处。
3. 接口向后兼容（不破坏旧的单字段 `message` 用法）。
4. 补齐**单元测试 + 集成测试**，覆盖率 **≥ 30%**，并给出明确验收标准。

## 二、接口设计

### 2.1 核心接口

| 属性 | 值 |
| --- | --- |
| 请求方式（HTTP Method） | **POST** |
| 请求路径 | `/api/chat` |
| 请求体 Content-Type | `application/json` |
| 登录/鉴权 | 无（沿用现状，靠 `sessionId` 区分会话） |

### 2.2 请求入参（`ChatRequest`，改造为 record）

```json
POST /api/chat
Content-Type: application/json

{
  "message": "厦门理工学院创建于哪一年？",
  "sessionId": "a1b2c3d4",      // 可选；空/缺省 = 开启新会话
  "ragEnabled": true,            // 可选，默认 true；false 则纯对话不走知识库
  "topK": 5                      // 可选，默认 5；RAG 检索条数
}
```

字段说明：
| 字段 | 类型 | 必填 | 默认 | 约束 |
| --- | --- | --- | --- | --- |
| `message` | String | 是 | — | 非空、去除首尾空格后长度 ≥ 1，长度上限 4000 |
| `sessionId` | String | 否 | 服务端生成 | 空/缺省则由后端生成并随响应返回 |
| `ragEnabled` | Boolean | 否 | `true` | — |
| `topK` | Integer | 否 | `5` | `1 <= topK <= 20` |

### 2.3 响应出参（`ChatResponse`，改造为 record）

成功 `200 OK`：
```json
{
  "reply": "厦门理工学院（原鹭江职业大学）创办于 1981 年……",
  "sessionId": "a1b2c3d4",
  "sources": [
    { "content": "……", "source": "school_intro.txt", "score": 0.86 }
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `reply` | String | 模型回复 |
| `sessionId` | String | 业务需回传以延续同一次多轮会话 |
| `sources` | `List<SearchHit> \| null` | 仅 RAG 开启时返回命中知识（可空） |

### 2.4 错误响应（统一格式，新增轻量 `GlobalExceptionHandler`）

| 场景 | HTTP 状态码 | 返回体示例 |
| --- | --- | --- |
| `message` 缺失/全空白 | 400 | `{"code":400,"message":"message 不能为空","path":"/api/chat","timestamp":"2026-09-10T10:00:00"}` |
| `topK` 越界（<1 或 >20） | 400 | `{"code":400,"message":"topK 必须在 1~20 之间",...}` |
| 请求体不是合法 JSON | 400 | `{"code":400,"message":"请求体格式错误",...}` |
| 不支持的 Content-Type | 415 | `{"code":415,"message":"Content-Type 必须为 application/json",...}` |
| 路径不存在 | 404 | `{"code":404,"message":"资源不存在",...}` |
| 模型/向量库/上游异常 | 500 | `{"code":500,"message":"服务处理失败",...}` |

### 2.5 辅助接口（会话管理，可选但建议一并实现）

| 接口 | 说明 |
| --- | --- |
| `DELETE /api/chat/sessions/{sessionId}` | 清空指定会话历史（204 无内容；会话不存在也返回 204，幂等） |
| `GET /api/chat/sessions/{sessionId}`（可选） | 查看某个会话已保留的历史条数/概览，便于排查 |

## 三、技术方案（多轮记忆 + RAG 融合）

采用既有可行性文档推荐的 **方案 B：服务端内存会话（Spring AI `ChatMemory`）**，零新增中间件，符合低成本、自托管偏好。

### 3.1 多轮记忆
- 注入内存版 `ChatMemory`（建议 `MessageWindowChatMemory`，滑窗保留最近 **10 轮 / 30 条** 消息，防本地小模型上下文溢出）。
- 每次请求：`MessageChatMemoryAdvisor` 按 `sessionId` 自动把历史消息注入提示词，调用后自动写回本条对话。
- 后端为空的 `sessionId` 生成一个 `UUID`，随响应返回，前端回传即可延续会话。

### 3.2 RAG 知识融合
- 循环内用 `QuestionAnswerAdvisor`（基于 `VectorStore`，`topK` 可配）自动检索顶层知识作为背景注入。
- 若 `ragEnabled=false`，则跳过该 Advisor，仅做多轮对话，保证向后兼容与灵活性。

### 3.3 代码改动点（预估）

| 文件 | 改动 | 预估 |
| --- | --- | --- |
| `ChatRequest.java` | 新增 `sessionId`、`ragEnabled`、`topK` 字段 + `@Schema` + 校验注解 | +20 行 |
| `ChatResponse.java` | 新增 `sessionId`、`sources` | +15 行 |
| `ChatConfig.java` | 新增 `ChatMemory` Bean；`chatClient` 保留 | +10 行 |
| `ChatService.java` | 注入 `ChatMemory`、`VectorStore`；方法改 `chat(message, sessionId, ragEnabled, topK)`；组装两个 Advisor | +35 行 |
| `ChatController.java` | `@Valid` 校验、生成/透传 `sessionId`、新增 2 个会话管理端点 | +25 行 |
| 新增 `GlobalExceptionHandler.java` | 统一异常转错误响应体 | +35 行 |
| 新增 `StubChatModel`（test） | 集成测试用固定响应模型 | — |

> 说明：Spring AI 2.0 的 `QuestionAnswerAdvisor` / `MessageChatMemoryAdvisor` 具体方法名以 IDE 实际解析为准，落地时校验。

### 3.4 关键风险与对策
| 风险 | 对策 |
| --- | --- |
| 本地小模型上下文溢出、历史越滚越长 | 滑窗限制最近 10 轮/30 条；必要时调小 |
| 内存会话重启丢失 | 接受（演示场景）；未来可升级数据库持久化方案 C |
| 模型冷加载/慢推理触发超时 | 沿用现有 `300s` 超时配置 |

## 五、验收标准（AC）

**功能**
- [ ] AC1 `POST /api/chat`（仅传 `message`）返回 `200`，`sessionId` 自动生成且非空。
- [ ] AC2 用同一 `sessionId` 连续提问 ≥ 3 轮，模型能基于前文回答（记忆生效），且不同 `sessionId` 互不串扰。
- [ ] AC3 `ragEnabled=true` 且知识库命中时，返回 `sources` 非空，回答可溯源；`ragEnabled=false` 时 `sources` 为 null。
- [ ] AC4 向后兼容：旧调用方只传 `message` 仍可用，返回结构仅**新增**字段、不删除旧字段。

**错误处理**
- [ ] AC5 空 `message`、`topK` 越界 → `400` 且返回统一错误体。
- [ ] AC6 非法 JSON → `400`；错误 Content-Type → `415`；上游异常 → `500`；统一错误体结构一致。

**测试与覆盖率**
- [ ] AC7 单元测试覆盖 4.2～4.5 全部用例；`mvn test` 全绿。
- [ ] AC8 集成测试（IT-1~IT-10）在**无需启动 LM Studio / Milvus** 的情况下全绿（桩替换外部依赖）。
- [ ] AC9 `mvn verify` 生成的 JaCoCo 报告**总行覆盖率 ≥ 30%**，且不触发 0.30 红线规则而失败。
- [ ] AC10 无回归：原有 `RagApplicationTests.contextLoads()` 通过。

**文档与接口**
- [ ] AC11 Knife4j/Swagger 页面能看到 `POST /api/chat` 的入参、出参、错误码说明。

## 七、需确认的决策点

1. **是否同时把知识库接入对话（RAG）？** → 本计划默认**是**（方案二你的知识已导入 Milvus，不接入则提问不会用到它）；若只需纯多轮对话，去掉 `QuestionAnswerAdvisor` 即可。
2. **多轮会话放哪？** → 默认服务端内存（零新增依赖，重启即失）；如需持久化再升级数据库方案。
3. **上下文范围？** → 默认最近 10 轮 / 30 条，可按模型表现调小。
4. **要不要 `DELETE /api/chat/sessions/{sessionId}` 清空会话接口？** → 默认实现（便于多轮演示时重置上下文）。

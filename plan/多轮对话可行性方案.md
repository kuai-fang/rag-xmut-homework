# 多轮对话升级 —— 可行性分析与实施方案

> 面向项目：`rag-xmut-main`（Spring Boot 4.1.1 + Java 21 + Spring AI 2.0 + Milvus）
> 目标：将现有**单轮对话**升级为**多轮对话**，并评估是否值得（及如何）融合知识库。
> 日期：2026-09-10

---

## 一、项目现状摘要

### 1.1 技术栈
| 组件 | 说明 |
| --- | --- |
| 框架 | Spring Boot 4.1.1 / Java 21 |
| AI 框架 | Spring AI 2.0.0（`spring-ai-starter-model-openai`） |
| 对话模型 | `google/gemma-4-e4b`，本地 LM Studio 托管（OpenAI 兼容协议） |
| 向量模型 | `text-embedding-bge-m3`（1024 维） |
| 向量库 | Milvus 3.0.1（docker-compose 自托管，集合 `knowledge_base`） |
| API 文档 | Knife4j（Swagger UI） |
| 文档解析 | Tika |

### 1.2 现有链路分析
```
聊天链路（无知识库）：
  前端 → ChatController.chat(message) → ChatService.chat(message) → ChatClient 直接发给模型 → 返回回复

知识库链路（未接入对话）：
  文档 → RagKnowledgeService.importDocument(分块500/重叠120 → bge-m3 嵌入 → 写 Milvus)
  RagKnowledgeService.search(query, topK) → Milvus 向量检索（该能力存在但从未被 chat 调用）
```

### 1.3 关键现状结论
1. **对话为纯单轮**：`ChatService` 每次只把 `message` 发给模型，无任何历史记忆（`ChatController` 第 27 行注释明确写明"无上下文记忆"）。
2. **知识库与对话脱节**：`RagKnowledgeService.search()` 已具备语义检索能力，但 `ChatService` 没有调用它。也就是说，**当前导入的向量知识无法在对话中使用**，这是比"多轮"更值得顺手解决的问题。
3. 对话模型是**本地小模型** `gemma-4-e4b`，其上下文窗口有限，多轮记忆累积需控制窗口长度（见 3.4 风险）。

## 二、需求理解

用户想要的核心能力：
- **多轮对话**：后续提问能"记得"前面说过什么，实现连续、有来有回的自然对话。
- 项目已有：单轮对话 + 知识库向量导入/检索。

隐含的合理预期（结合本项目定位）：
- 多轮对话最好能**同时结合知识库**，让 RAG 能力真正进入对话（否则"导入知识库"的意义仅停留在 `/api/rag/search` 检索接口上）。

---

## 三、多轮对话技术方案选型

Spring AI 2.0 提供了多种多轮实现方式，按"耦合度/复杂度"由低到高列出：

| 方案 | 记忆在哪里 | 前端改动 | 后端改动 | 持久化 | 适合场景 |
| --- | --- | --- | --- | --- | --- |
| **A. 无状态传历史**（消息由前端维护） | 前端（每次请求带完整 messages 数组） | 需维护历史数组 | 最小，仅把 `ChatRequest.message` 扩成 `messages` 列表 | 无 | 演示/轻量场景 |
| **B. 服务端内存会话**（Spring AI `ChatMemory`） | 服务端内存（按 `sessionId` 划分） | 增传 `sessionId` | 中等，注入 `MessageWindowChatMemory` + `MessageChatMemoryAdvisor` | 无（重启即失） | **本项目推荐** |
| **C. 服务端数据库会话** | 数据库/Redis | 同 B，传 `sessionId` | 较大，需新增存储、会话表 | 有 | 生产/多端共享 |
| **D. 升级为流式多轮**（SSE） | 依上 | 需处理流式渲染 | 相应改造 | — | 追求打字机体验时叠加 |

### 3.1 方案推荐：B（服务端内存会话）+ 可选升级 C

理由：
1. **符合用户偏好**（低成本、自托管、先核心功能）：方案 B 无需引入任何新中间件或数据库，仅用 Spring AI 自带的 `ChatMemory` 机制即可实现，改动面小、技术栈零新增。
2. **调用贴合现有代码**：只需给 `ChatService` 增加一个 `sessionId` 参数，并接入 `MessageChatMemoryAdvisor`，`ChatClient` 会自动在每次调用前拼接历史消息，业务代码几乎不用改写构建逻辑。
3. **保留升级路径**：未来如需持久化，把 `ChatMemory` 换成数据库实现（方案 C）或加 Redis，`Advisor` 与 Controller 签名不变，属增量改造。

### 3.2 对照现有代码的具体改动点

| 现有文件 | 改动 | 说明 |
| --- | --- | --- |
| `ChatRequest.java` | 字段 `message` 扩为 `messages`（List）或保留 `message` 并新增 `sessionId` | 二者选一。**推荐保留 `message` + 新增 `sessionId`**：改动最小、兼容旧前端。 |
| `ChatResponse.java` | 可新增 `sessionId` | 首次无 session 时由后端生成并返回，前端回传即可。 |
| `ChatService.java` | `chat(message)` → `chat(message, sessionId)`；用 `ChatClient` + `MessageChatMemoryAdvisor` | 核心改动（约 +20 行，见下）。 |
| `ChatConfig.java` | 新增 `ChatMemory`（`ConcurrentWindowChatMemory`）与 `Advisor` Bean | 约 +10 行。 |
| `ChatController.java` | 透传/兜底 `sessionId`（无则生成） | 约 +10 行。 |

### 3.3 Spring AI 2.0 核心代码示意（落地框架）

```java
// ChatConfig.java —— 新增
@Bean
ChatMemory chatMemory() {
    return new ConcurrentWindowChatMemory(ChatMemorySize.windows(10, 30)); // 最近 10 轮/30 条
}
@Bean
MessageChatMemoryAdvisor chatMemoryAdvisor(ChatMemory chatMemory) {
    return new MessageChatMemoryAdvisor(chatMemory);
}

// ChatService.java —— 改造
public ChatResponse chat(String message, String sessionId, MessageChatMemoryAdvisor advisor) {
    String reply = chatClient.prompt()
            .advisors(a -> a.advisors(advisor).param(ChatMemory.CHAT_MEMORY_CONVERSATION_ID_KEY, sessionId))
            .user(message)
            .call()
            .content();
    return new ChatResponse(reply, sessionId);
}
```

> 说明：`MessageChatMemoryAdvisor` 会在模型调用前自动从 `ChatMemory` 取出该 `sessionId` 的历史消息、拼进提示（并在调用后把本条对话写回），从而天然实现多轮。具体 API 名称以引入的 Spring AI 2.0 版本为准，落地时以 IDE 自动补全校验。

### 3.4 关键技术风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **上下文窗口有限** | `gemma-4-e4b` 本地模型窗口有限，历史越滚越长易触发截断/降智 | 用 `MessageWindowChatMemory` 滑动窗口（如保留最近 N 轮）；必要时调小窗口 |
| **内存会话丢失** | 服务重启后历史清空 | 接受（演示场景）或后续升级方案 C |
| **鉴权/并发** | 无用户体系时靠 `sessionId` 区分会话 | 单机 `ConcurrentWindowChatMemory` 已线程安全；无需额外处理 |
| **长响应超时** | 模型冷加载/慢推理可能触发 300s 超时 | 沿用现有 `spring.ai.openai.timeout=300s` 配置即可 |

## 四、跨链整合建议（强烈建议一并纳入）

现状的"知识库"与"对话"是两条平行线。既然要做多轮，**天然该把 RAG 检索接进对话**，形成"多轮 + 知识增强问答"。改造成本很低：

```
多轮 RAG 对话链路（目标态）：
  message+sessionId → ① 向量检索知识库(复用 RagKnowledgeService.search，topK 取 3~5)
                     → ② 检索结果拼入 SystemMessage 作为"背景知识"
                     → ③ 连同历史消息一并发给 gemma (Advisor 注入历史)
                     → ④ 返回回复
```

- 只需在 `ChatService` 中注入 `RagKnowledgeService`，将 `search(message, 5)` 的结果格式化后作为 `SystemMessage` 前缀注入。
- **零新增依赖**，复用现有 `bge-m3` + Milvus + `search()`。
- 收益大：让"导入知识库"真正服务于对话，本项目核心价值提升最明显的一点。

## 五、可行性结论

**✅ 结论：完全可行，且工作量小、风险低。**
- 多轮对话是 Spring AI 2.0 的标准能力，项目已具备全部前置依赖（ChatClient、本地模型、无新增中间件）。
- 核心改动集中在 4 个已有文件，预计纯代码改动 **约 40~60 行**。
- 知识库接入对话为**可选增强**，额外改动约 20 行，深度复用已有 `search()` 能力，强烈建议一并做。

| 规模 | 预估工作量 |
| --- | --- |
| 仅多轮对话（方案 B） | 0.5 ~ 1 人日 |
| 多轮对话 + 知识库融合 | 1 ~ 1.5 人日 |
| 追加会话持久化（方案 C） | 额外 +1 ~ 2 人日（本项目暂不建议） |

## 六、分阶段实施计划（按优先级）

- **[P0] 阶段一：多轮对话落地（方案 B）**
  1. 改 `ChatRequest`/`ChatResponse`：增加 `sessionId`。
  2. `ChatConfig`：注册 `ChatMemory`（滑动窗口）+ `MessageChatMemoryAdvisor`。
  3. `ChatService`：方法签名加 `sessionId`，接入 Advisor；`ChatController` 生成/透传 `sessionId`。
  4. 用 Knife4j 手动验证多轮上下文是否生效（连续提问能否记住前文）。
- **[P0] 阶段二：RAG 融入对话**（推荐同时完成）
  5. `ChatService` 注入 `RagKnowledgeService`，检索 topK 知识 → 注入 SystemMessage。
  6. 验证：先导入知识库，再就库内知识连续追问，确认回答基于知识库且有记忆。
- **[P1] 可选：流式输出（SSE）**，提升交互体验。
- **[P2] 可选：会话持久化（方案 C）**，仅当有多端/重启保留需求时再实施。

## 七、需用户确认的关键决策

1. **是否同时把知识库接入对话？**（强烈建议 yes——否则导入的知识只停在检索接口，价值没打通）
2. **会话状态放哪？** 默认服务端内存（方案 B，零新增依赖）；如需要重启后仍记得，需升级方案 C（引入数据库）。
3. **上下文保留范围？** 默认滑窗"最近 10 轮/30 条"，可按模型表现调小。
4. **接口兼容？** 推荐向后兼容：保留旧的 `message` 单字段用法，`sessionId` 可空（空则视为新会话）。
